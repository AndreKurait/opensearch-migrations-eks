## Plan a migration around your data and workload

Migration Assistant provides workflows for snapshot-based backfill and traffic capture/replay. Choose a workflow after checking the source and target versions, required transformations, and application requirements.

This site is an independent documentation prototype. Confirm commands and compatibility against the selected [upstream release](https://github.com/opensearch-project/opensearch-migrations/releases) before using them.

<Aside type="tip" title="The key insight">
  Snapshot backfill reads snapshot data rather than performing the bulk document read through the source cluster. Snapshot creation, traffic capture, validation, and cutover can still affect a running system. Test those operations and their permissions before production use.
</Aside>

## What Scares You Most?

These are migration planning concerns to evaluate in a staging environment.

<CardGrid>
  <Card title="We can't afford downtime" icon="approve-check-circle">
    Capture/replay workflows aim to reduce the write pause during migration. Availability still depends on capture coverage, replay correctness, traffic routing, and the cutover procedure. Validate those conditions before promising uninterrupted service.
  </Card>
  <Card title="Our version gap is too wide" icon="random">
    Check the exact source/target pair against the selected release. Mapping transformations, plugins, index formats, and application behavior can impose additional requirements; a broad version range does not establish compatibility for your data.
  </Card>
  <Card title="What if it corrupts our source?" icon="warning">
    Snapshot backfill reads a snapshot copy. The overall migration can still involve source snapshot operations, traffic capture, and validation requests. Review permissions, test operational impact, and retain backups.
  </Card>
  <Card title="What if it fails halfway through?" icon="rocket">
    Inspect the workflow state and the selected release's retry/resume behavior before restarting. Test failure recovery on representative data; do not assume every operation is idempotent or every destructive step has an approval gate.
  </Card>
</CardGrid>

## What Happens If Something Goes Wrong?

Prepare a recovery procedure before starting the migration:

<Steps>
1. **Understand source impact.** Snapshot backfill and traffic capture have different operational effects. Test snapshot creation, capture, and validation separately.

2. **Check recovery behavior.** Confirm which workflow steps can retry or resume for your release and inspect their recorded state before rerunning them.

3. **Review workflow controls.** Inspect the actual workflow for approval gates and destructive actions. Add operational review where your migration requires it.

4. **Validate before switching.** Compare document contents, counts, mappings, and representative queries. Confirm application behavior and investigate discrepancies before redirecting traffic.

5. **Rehearse rollback.** After cutover, new writes may exist only on the target. Redirecting traffic back can lose access to those updates unless your recovery plan reconciles them. Define rollback criteria, data handling, and routing steps in advance.
</Steps>

<Aside type="caution" title="The one thing you should plan for">
  The traffic capture proxy sits in the request path. Measure latency, failure behavior, and capture coverage with representative traffic before production use.
</Aside>

## Migration workflow

<Steps>
1. **Deploy** — Follow the bootstrap or Helm instructions for the selected release and connect to the Migration Console.

2. **Configure** — Define your source snapshot location, target OpenSearch endpoint, and migration options using that release's configuration schema.

3. **Migrate** — Review and submit the workflow, then monitor metadata migration, backfill, and any capture/replay operations.

4. **Validate & Switch** — Complete data and application checks, then follow the rehearsed cutover procedure.
</Steps>

## Which Path Is Right for You?

<Tabs>
  <TabItem label="Backfill Only">
    **Consider when:** You can plan a write pause or otherwise reconcile changes made after the snapshot.

    **How it works:**
    1. Take a snapshot of the source cluster
    2. Migrate index metadata to the target
    3. Backfill the selected snapshot data
    4. Verify document counts and queries
    5. Switch traffic to the target

    **Trade-off:** Writes made after the snapshot are not included in that snapshot. Plan a write pause or a separate way to reconcile them before cutover.

    <LinkCard title="Backfill-Only Guide →" description="Workflow overview and CLI examples to verify against your release" href="/opensearch-migrations-eks/migration-guide/backfill/" />
  </TabItem>
  <TabItem label="Capture and Replay">
    **Consider when:** You need to reduce the write pause and can validate traffic capture, replay, and cutover behavior.

    **How it works:**
    1. Deploy the traffic capture proxy in front of your source
    2. Take a snapshot while traffic is being captured
    3. Migrate metadata and backfill from the snapshot
    4. Replay captured traffic to close the gap
    5. Verify, then switch traffic to the target

    **Trade-off:** More moving parts and a proxy in the request path. Measure latency and validate capture coverage, replay behavior, and data consistency.

    <LinkCard title="Capture and Replay Guide →" description="Workflow overview including traffic capture setup" href="/opensearch-migrations-eks/migration-guide/capture-and-replay/" />
  </TabItem>
</Tabs>

## Performance at Scale

Measure throughput with representative data and the intended target cluster. Worker count alone does not establish an end-to-end completion time.

| Factor | What to measure |
| --- | --- |
| Documents and mappings | Sizes, transformations, and indexing cost |
| Snapshot and network | Read throughput and transfer limits |
| Target cluster | Sustained write capacity and rejected requests |
| Workers and shards | Utilization, concurrency, and uneven shard sizes |

<Aside type="note">
  Record the release, dataset, hardware, worker count, target configuration, and validation results when sharing a benchmark. This page does not provide a reproducible throughput benchmark.
</Aside>

## Version Compatibility

Check the selected upstream release's compatibility documentation and test your exact source/target pair. This prototype does not establish a universal compatibility matrix.

Include index creation versions, plugins, mappings, and required migration features in that check. A successful document backfill alone does not establish application compatibility.

Check Kubernetes, Helm, storage, networking, and IAM prerequisites for the chosen deployment environment and chart version.

## What Gets Migrated

<Tabs>
  <TabItem label="Migration Scope">
    Check which of these components your selected release and workflow handle, and validate the results:

    - **Documents** — Snapshot data selected for backfill
    - **Index settings & mappings** — Required target-version transformations
    - **Index templates** — Legacy and composable template handling
    - **Component templates** — Shared template building blocks
    - **Aliases** — Alias definitions and intended routing behavior
  </TabItem>
  <TabItem label="Manual Setup Required">
    These components need to be recreated manually on the target cluster:

    - ⚠️ **ISM / ILM policies** — Index lifecycle management policies differ between Elasticsearch and OpenSearch
    - ⚠️ **Security configuration** — Users, roles, and auth backends need manual setup
    - ⚠️ **Kibana / Dashboards objects** — Saved searches, visualizations, dashboards
    - ⚠️ **Ingest pipelines** — May need syntax adjustments for OpenSearch
    - ⚠️ **Data streams** — Require manual recreation on the target

    <Aside type="tip">
      Estimate manual work from your configuration and application dependencies. See the [pre-migration checklist](/opensearch-migrations-eks/overview/migration-paths/) for topics to review.
    </Aside>
  </TabItem>
</Tabs>

## Prerequisites

:::note[Before you deploy]
- **Kubernetes cluster** meeting the selected chart's requirements, with permissions to deploy it
- **kubectl** and **Helm 3** installed locally
- **Source and target clusters** supported by the selected release, with the connectivity required by your workflow
- A **snapshot in S3** — or the ability to create one ([snapshot guide](/opensearch-migrations-eks/deployment/deploying-to-eks/))
:::

<Aside type="tip" title="Already deployed?">
  Reconnect to your Migration Console: `kubectl exec -it migration-console-0 -n ma -- bash` then run `workflow configure sample` to see the config schema for your version.
</Aside>
